# 实测数据与成本算法

实测环境：macOS，227 个会话（Codex 211 + WorkBuddy 73，去重后 227）。

| 项目 | 数据 | 口径 |
|---|---|---|
| 全量构建 | **2.0 秒** | 含 SQLite 库扫描 |
| 增量重建 | **0.3–1.4 秒** | 来源未变则直接复用缓存 |
| 单次检索定位 | **17 毫秒** | grep 主题页 |
| 产出 | 28 个主题页 / 39,691 tokens | 压缩比 **56.6 : 1** |
| 典型会话 | 1,547 tokens | 中位数 |
| 典型页 | 1,266 tokens | 中位数 |
| 建库消耗 token | **0** | 无任何网络请求 |

## 三种读法的成本

「毛省」只算读页；「净省」把技能正文的加载成本（1,400 token）也算进去——那才是账单上的数。

| 场景 | 不用技能 | 毛成本（页/行） | 净成本（含说明 1,400） | 毛省 | **净省** |
|---|---|---|---|---|---|
| 替代 2 个中位会话 | 3,094 | 1,266 | 2,666 | 59% | **14%** |
| 替代 1 个大会话 | 29,610 | 1,266 | 2,666 | 96% | **91%** |
| 只读命中行 | 3,094 | 241 | 1,641 | 92% | **47%** |
| 同一会话回溯 3 次 | 9,282 | 3,798 | 5,198 | 59% | **44%** |

> 说明成本每会话只付一次，回顾次数越多越划算——这正是「一次会话里多次追问」的设计前提。
> 对外只说净省区间（14–91%），不说「省 98%」。

## 技能自己的开销也要算

用了技能，模型就要读这份说明。这笔钱不装技能时不存在，所以必须计入回本比：

```
回本比 = (2 × 典型会话) ÷ (典型页 + overhead_tokens)
       = 3,094 ÷ (1,266 + 1,400)
       = 1.16      → active
```

`overhead_tokens` 默认 1,400，对应实测的 SKILL.md 正文 1,277 token（tiktoken cl100k 实测）
加上约 10% 余量。正文变长就要调高它，否则会高估收益。

三项同时成立才允许启用：会话 ≥ 20、压缩比 ≥ 8:1、回本比 ≥ 1.0。

语料太小时读页就不划算了（实测 8 个会话：压缩比 1.0、回本比 0.12），
所以 `gate.json` 一票否决——这是机制说明，不是缺陷清单。
